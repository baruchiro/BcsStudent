כשהסוכן כותב את הקוד, אני כמעט לא כותב. מה שנשאר לי הוא ריביו, כל הזמן. כשאני מריץ כמה משימות במקביל, כל פעם מגיעה אליי כמות גדולה של קוד, ואני חייב למצוא דרך להתמודד איתה.

הפוסט הזה מתאר את הדרך שלי. היא לא מנסה להוציא אותי מהלולאה, אלא לוודא שאני מסתכל רק על מה שבאמת צריך אותי.

## קודם כול: PR קטן אחד לכל חתיכה

הצעד הראשון הוא לא כלי. אני מבקש מהסוכן לפצל כל פיצ'ר קטן לPR נפרד, כדי שאוכל לעשות ריביו לכל שינוי בנפרד ולא לעבור על 50 קבצים בבת אחת. [GitHub](https://github.com/) הוסיפו פיצ'ר של stack, שמאפשר לפתוח PR אחד על גבי השני, וזה מתאים בדיוק לזה.

במשימת fullstack אני יכול בקלות להחזיק 8 PRs: למשל שניים בfrontend ושישה בbackend. כל מה שנשאר אחר כך הוא ניהול הריביו עליהם.

## שני סבבים, ואני בשניהם

לכל PR יש אצלי שני סבבים.

**הסבב הראשון הוא ריביו ידני.** PR מחכה לי, אני עושה לו ריביו ומשאיר הערות, קלוד לוקח את ההערות ומתקן, ואז הוא שוב מחכה לי. ככה עד שאני מרוצה. רק אז אני מעביר את הPR לready for review.

**הסבב השני הוא הריביו האוטומטי.** מעבירים את הPR לready, וכלים כמו [CodeRabbit](https://www.coderabbit.ai/) מתחילים להעיר. ראיתי שהכלים האלה עלולים להיכנס ללולאה או להעיר הערות לא נכונות, אז אני לא נותן לקלוד לפעול על כל הערה. אני עובר על ההערות של CodeRabbit ממש ברפרוף, ומסמן 👍 על אלה שנכונות. רק אותן קלוד יכול לקחת.

ככה אני נשאר הסוקר שמחליט, גם כשחלק גדול מהעבודה נעשה בלעדיי.

## הסקיל שמרוקן את ההערות

את החלק של "קלוד לוקח את ההערות" אני לא משאיר לאלתור. יש לי plugin בשם `pr-review-loop`, והסקיל `resolving-pr-review-comments` שבו עושה את העבודה בכמה שלבים:

- סקריפט (לא שיקול דעת של מודל) מביא רק threads שפתוחים ושדורשים פעולה עכשיו. הוא מדלג על threads שהסוכן כבר ענה עליהם אחרון, ועל הערות של CodeRabbit שלא סימנתי עליהן 👍.
- הסוכן מקבץ את ההערות לקבוצות קטנות, וסוכן נפרד מטפל בכל קבוצה במקביל: או מתקן בקוד או עונה.
- thread נסגר רק אם התשובה או התיקון לא הוסיפו משהו שאני עוד צריך לראות. אם הסוכן מעלה שאלה או התלבטות, הוא משאיר את הthread פתוח. זו ההחלטה שלי, לא שלו.
- הסוכן בודק גם CI, ודוחף את התיקונים לפני שהוא מכריז שהסתיים. CI ירוק על commit ישן לא אומר כלום על התיקון החדש.

הסקיל מתעד גם מה המשמעות של תוצאה ריקה: הסקריפט החזיר `[]` כלומר אין הערות actionable לפי הסינון. זה לא אומר שהריביו האנושי הסתיים. את זה רק אני יודע.

## מאיפה מתחילים לקרוא 50 קבצים?

גם אחרי שפיצלתי, לפעמים PR עדיין גדול. GitHub מציג את הקבצים לפי סדר אלפביתי, וזה כמעט אף פעם לא הסדר שמקל על קריאה.

כאן נכנס [pr-review-sorter](https://github.com/BnayaZil/pr-review-sorter) של בניה ([@BnayaZil](https://github.com/BnayaZil)). זה סקיל לClaude Code יחד עם תוסף Chrome. הסוכן מסתכל על הPR ומחליט על סדר קריאה: נקודות כניסה קודם, בדיקות ותיעוד בסוף, עם סיבה קצרה לכל קובץ. הוא יכול גם להדגיש שורות ולהוסיף הערות inline שמובילות אותי בדיף.

כל זה מקודד בקישור אחד, בצורה `github.com/.../files#pr_order=...`. אין API ואין שרת. כשאני פותח את הקישור, התוסף מסדר מחדש את רשימת הקבצים, ממספר אותם ומצייר את ההדגשות. אני גם לא צריך לבקש את זה כל פעם: הסדר נשמר בדפדפן לפי PR.

## לדעת של מי התור

החלק שהכי קל לטעות בו בסבבים האלה הוא לשמור בראש איזה PR מחכה לי, באיזה קלוד עובד עכשיו, ואיזה כבר מוכן. הסקיל כותב את המצב לקובץ `pr-status.json`, ואת הקובץ הזה מציג תוסף VS Code שלי, [PR Review Loop](https://marketplace.visualstudio.com/items?itemName=baruchiro.pr-review-loop) ([הקוד](https://github.com/baruchiro/pr-status-vscode)).

למעלה מופיע הPR הבא שצריך אותי, ומתחתיו כל הPRs לפי סדר הטיפול, כל אחד עם סטטוס שמראה של מי התור: שלי, של קלוד, של CI או של CodeRabbit. התוסף מתרענן לבד, ומראה גם מתי יש שינויים מקומיים שעוד לא נדחפו. התמונה היא מהתיעוד של התוסף, עם PRs לדוגמה.

להתקנה צריך את `gh` ו־`jq`, ואת הplugin:

```bash
claude plugin marketplace add baruchiro/skills && claude plugin install pr-review-loop@skills
```

## הכול ביחד: /goal אחד שחוזר

את החלקים האלה אני מחבר עם `/goal` של Claude Code, שמפעיל את הסקיל שוב ושוב עד שתנאי הסיום מתקיים. זה הנוסח שלי, כמו שהוא:

```text
/goal drain /baruchiro:resolving-pr-review-comments on all PRs for the current workspace — commit and push any fixes; at the end of every pass run pr-status.sh for all those PRs and give me the ~/.claude/pr-status.md link, and for each PR whose diff changed in the pass and has more than 5 files, regenerate the /pr-review-sorter link; done when the fetch script returns [] for all and CI check runs are all success on all against the latest pushed commit
```

כמה דברים שכדאי לשים לב אליהם:

- **commit ו־push כתובים במפורש.** הסקיל בדרך כלל מבקש אישור לפני commit. כשזה כתוב בתנאי, זו הרשאה, והלולאה יכולה להמשיך בלי שאעצור אותה.
- **בסוף כל סבב מגיע קישור לדוח המצב**, גם אם שום דבר לא השתנה, כדי שאוכל להרים את החוט במקום שבו עצרתי. הנתיב `~/.claude/pr-status.md` הוא כמו שכתוב בפקודה שלי. בגרסה הנוכחית של הסקיל ברירת המחדל היא תיקיית הפרויקט, אפשר לשנות אותה עם `PR_STATUS_FILE`.
- **קישור חדש לsorter רק לPR שהשתנה ושיש בו יותר מ־5 קבצים.** קישור ישן מצביע על diff שכבר לא קיים, והתוסף מסמן אותו `stale`.
- **תנאי הסיום ניתן לבדיקה:** הסקריפט החזיר `[]` וכל בדיקות הCI הצליחו על הcommit האחרון שנדחף. `/goal` שופט את התנאי לפי מה שכתוב בשיחה, אז הסקיל מתבקש לכתוב את התוצאה בטקסט בסוף כל סבב.

שום דבר בתנאי הזה לא ממזג. מיזוג הוא עדיין ההחלטה שלי, אחרי שעברתי על הקבצים.

## מה שעדיין לא פתור

הנקודה שהכי מציקה לי היא הסימון של 👍 על הערות CodeRabbit. אני עושה אותו ברפרוף כי עוד אין לי דרך לסמוך על הריביו האוטומטי, והוא באמת לפעמים טועה. אבל ריפרוף הוא עדיין צעד אנושי בכל סבב. אם יש לכם כלל החלטה לגבי מתי אפשר להפסיק לבדוק הערות אוטומטיות אחת אחת, אשמח לשמוע איך הגעתם אליו.
